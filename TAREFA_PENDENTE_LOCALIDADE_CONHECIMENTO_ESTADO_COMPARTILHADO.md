## Decisão registrada em 2026-08-06 (conversa, formalizada aqui)

Pedido: a arquitetura rica (contrato de `RelacaoEstruturalTransformacao` — `calcularValorAusente`/`aplicar`/`EstadoConsistencia`/`DiagnosticoErroPapel`) deve ser implementada **integralmente** para as três categorias aditivas (Composição, Transformação, Comparação), e `Main.java` deve ficar "só com o código necessário", seguindo fielmente o princípio da localidade do conhecimento já citado em `REFERENCE.md`. Isso implica migrar o uso de produção de `EstadoSemanticoCompartilhado` para os objetos de domínio do pacote piloto (`gerard.dominio.campoaditivo`), não só criar Comparação isolada.

**[EVIDÊNCIA NO CÓDIGO]** `EstadoSemanticoCompartilhado` já é genérica para as três categorias via `TipoSituacaoAditiva` + `CatalogoEsquemasCategoriasAditivas.obter(tipo).obterDominioCompartilhado(indice)` — não é uma classe por categoria como o pacote piloto. É um estado único, mutável, `synchronized`, versionado por `Snapshot`, que resolve a relação aditiva genericamente (soma/subtração entre os três papéis) para qualquer uma das três categorias, dependendo de qual dos três valores está "alterado" (`indiceAlterado`) — a mesma classe já atende Composição, Transformação e Comparação em produção hoje.

Isso é estruturalmente diferente do pacote piloto (uma classe `RelacaoEstruturalX` por categoria, com objetos `PapelQuantitativo` individuais, eventos publicados, `DiagnosticoErroPapel`). Migrar "fielmente ao princípio da localidade do conhecimento" significa decidir **como** essas duas arquiteturas convergem — não é uma troca mecânica de chamada.

## Por que isto não pode ser um diff único, sem compilação intermediária

- 70 pontos de uso em 8 arquivos, a maior parte em `Main.java` (13.000+ linhas), em código de produção que sincroniza a tela usada para coleta de dados de pesquisa real (protocolos reais de participantes, ver `protocolos_reais_replay.tsv`).
- Não há capacidade de compilar Java neste ambiente onde a investigação foi feita (sem JDK, sem acesso root para instalar) — qualquer diff gerado aqui não pode ser verificado antes de chegar até você.
- O próprio processo já em uso neste repositório (`TAREFA_PENDENTE_COMPARACAO_MEDIDAS.md`, seção "Processo a seguir") exige compilação e harnesses rodados **antes e depois de cada mudança** — uma mudança desse tamanho, feita de uma vez, tornaria impossível isolar o que quebrou, se algo quebrar.

## Desdobramentos 2026-08-06 (tarde) — por que a Fase B2 literal ficou parada

A discussão sobre reduzir `Main.java` (por que é tão grande) levou por um caminho diferente do B2 original, registrado aqui para não se perder:

1. **Facade/árvore-B/"main deve chamar, não conter"**: discussão de arquitetura (Facade, árvore n-ária, árvore B como modelo estrutural, não como algoritmo) convergiu na regra explícita do usuário: **"o que for da main, deixe nela"**. Aplicando essa regra à maquinaria de sincronização do campo aditivo (`aplicarEstadoCompartilhadoEmTodasAsRepresentacoes`, `sincronizarElementosSemanticosDoTexto`, `sincronizarEixosComEstadoCompartilhado`, linhas ~7200-7300), a conclusão foi: quase todo esse código é legitimamente orquestração Swing da própria Main (ler/escrever widgets) — a lógica de domínio já está extraída (via B1). **Não há mais extração de valor nessa área específica.**
2. **"Gerard é essencialmente interação/protocolos de mouse"**: hipótese testada com evidência — `TelaGerard` implementar `MouseListener`/`MouseMotionListener`/`KeyListener` é estrutural do Swing (não extraível), mas os handlers de mouse (`mousePressed` etc.) são despacho de hit-test/seleção/log de pesquisa, não "estilo de interação". Achado concreto: `desenharPistaVisualDoModo` duplicava o despacho por `EstiloInteracao` que `EstrategiaEstiloInteracao.calcularEstado` já fazia — só para decidir o desenho, não o estado. **Extraído e commitado** (`e8ec816`) — ver `RELATORIO_EXTRACAO_DESENHO_ESTILO_INTERACAO_2026-08-06.md`. `Main.java`: 13.662 → 13.593 linhas.
3. **Bug de UI encontrado durante teste manual — corrigido**: limite superior de arraste de palavra do enunciado sobrepunha a barra de ícones Medidas/Relações. Primeira correção só somou a constante que faltava (`e89e718`); questionada pelo usuário ("por que não relativo à área real?"), foi refeita eliminando a segunda cópia da geometria — `TOPO_AREA_ENUNCIADO`/`BASE_AREA_ENUNCIADO` viraram fonte única, usada tanto por `estaNaAreaDoTexto` quanto pelo clamp de arraste (`cfe582b`). Ver `RELATORIO_BUG_LIMITE_SUPERIOR_ARRASTE_TEXTO_ENUNCIADO_2026-08-06.md`.
4. **"Estado modificado" — completo (alvo recalculado + registro de auditoria)**: encontrado durante o mesmo teste manual — mudar um papel-dado (ex.: Transformação) por outra representação (eixo x) deixava a pergunta de confirmação da incógnita comparando contra o curado original, gerando falso positivo. Parte 1 (`d70a5c4`): `valorDigitadoCorrespondeAoCurado` passou a usar `obterValorAlvoParaPapel`, que recalcula o alvo a partir do `Snapshot` atual quando disponível, caindo no curado só quando não há papéis-dado suficientes conhecidos ainda — ver `RELATORIO_ESTADO_MODIFICADO_ALVO_RECALCULADO_INCOGNITA_2026-08-06.md`. Parte 2, pedida na sequência (`f47ad24`): `EstadoPosicionamentoModelagem` ganhou o campo `estadoModificado` (para qualquer papel, não só a incógnita), e `registrarPapeisDadoModificadosSeHouver` registra um log de sistema quando a incógnita é submetida com algum papel-dado divergente do curado — ver `RELATORIO_ESTADO_MODIFICADO_REGISTRO_AUDITORIA_2026-08-06.md`.
5. **Nova skill `gerard-posicionamento-relativo`** (`d758c26`, `.claude/skills/`): captura o princípio do item 3 — posição/limite de qualquer elemento deve derivar da geometria real do contêiner, nunca de um número de pixel copiado — para carregar automaticamente em sessões futuras que mexerem em posicionamento/layout.

**Fase B2 literal (`Main.java` manipulando os objetos do piloto diretamente) continua não autorizada e sem decisão tomada** — a conversa não voltou a ela; a tarde toda foi para os achados de teste manual acima.

## Desdobramentos 2026-08-06 (noite) — plano de 3 passos para retomar a fronteira Main↔piloto

Revisitada a Fase B2 literal. Investigação (só leitura) encontrou evidência decisiva no próprio código: `PapelQuantitativo` (piloto) documenta em javadoc que é "isolado por design: não é referenciado por Main.java nem por nenhum caminho de produção", tratando reuso entre esquemas como "hipótese arquitetural ainda não validada"; e `TipoErroPapel` tinha só 1 valor, insuficiente para qualquer diagnóstico real de erro do estudante. Diante disso, o usuário definiu a ordem explícita:

1. **Enriquecer o piloto primeiro** — dar mais valores reais a `TipoErroPapel`/`DiagnosticoErroPapel`, zero risco de produção, mesmo espírito da Fase A. **Concluído** (commit a seguir): `TipoErroPapel` ganhou `OPERACAO_INVERTIDA` e `VALOR_INCORRETO` (de 1 para 3 valores); as 6 classes `RelacaoEstrutural*` ganharam `diagnosticarValorProposto(...)`, que avalia um valor proposto (não só calcula o que falta) e distingue correto / fora do domínio / operação invertida / genericamente errado. Ver `RELATORIO_ENRIQUECIMENTO_TIPOERROPAPEL_DIAGNOSTICO_2026-08-06.md`. Cobertura de teste adicionada nos 6 harnesses `TestePiloto*.java`; projeto completo compilado (0 erros) e todos os 6 harnesses executados com sucesso.
2. **Adotar só `OrigemAcao` na Main** — tipar a origem das ações no lugar dos flags ad-hoc, cruzando a fronteira "isolado por design" de forma bem mais estreita que a B2 completa. **Concluído**: o flag ad-hoc real encontrado foi a distinção `registrarLogUsuario`/`registrarLogComputador` — dois métodos que decidiam qual `LoggerInteracaoGerard.registrar*` chamar puramente pelo nome do wrapper escolhido pelo chamador, sem nenhum valor tipado carregando essa decisão.
